### A Conceptual Map of the Tutorial Series

## What Is MuJoCo?

**MuJoCo** (Multi-Joint dynamics with Contact) = modeling framework + dynamics engine + simulator + visualizer, built around one core split:

```
robot description (MJCF)  →  MjModel   (static, never changes)
simulation state           →  MjData    (dynamic, updates every step)
physics/dynamics           →  mj_step() / mj_forward() / mj_kinematics()
control inputs              →  data.ctrl   (you write this)
contacts                    →  auto-detected from geometry, solved inside mj_step
visualization                 →  reads MjData only; never advances physics
```

Notebook progression: **01** = model/data/loop/control vocabulary (toy pendulums) → **02** = contact in isolation (falling box) → **03** = everything combined on a real 3-DOF robot arm hitting a cube.

## Notebook 01 — Introduction to MuJoCo

### Core Idea: Model/Data Split + the Simulation Loop

**MJCF (modeling language, XML):**
- `<mujoco/>` = minimal valid model. Everything lives under `<worldbody>` (= global origin).
- **`body`** = movable, inertial entity. **`geom`** = its visual/collision shape (a body can have several). **Body ≠ geom.**
- `MjModel.from_xml_string()`/`from_xml_path()` invokes the compiler → binary `MjModel`.

**`MjModel`** — static description (never changes during sim):
| Field | Meaning |
|---|---|
| `nbody`/`ngeom` | # bodies / geoms |
| `nq` | # generalized position vars |
| `nv` | # generalized velocity DOFs |
| `nu` | # actuators |
| `opt` | physics options (timestep, gravity, integrator) |

> **Key rule:** `nq`, `nv`, `nu` are independent counts — never assume they're equal (a free joint alone breaks `nq == nv`).

**DOF comes from joints, not bodies:**
- A body with geoms but **no `<joint>`** = 0 DOF, rigidly welded to parent.
- `<joint type="hinge" axis="..." pos="..."/>` inside a body is what adds motion.
- `<keyframe>` defines a named reusable initial state → load with `mj_resetDataKeyframe(model, data, 0)`.

**Named access:** `model.geom('name')`, wraps `mj_name2id(model, objtype, name)`. Calling with no name → `KeyError` listing valid names. Body `0` is always `world`, unrenamable.

**`MjData`** — mutable state + everything derived from it:
| Field | Meaning | Shape |
|---|---|---|
| `qpos` | generalized position | `(nq,)` |
| `qvel` | generalized velocity | `(nv,)` |
| `qacc` | generalized acceleration | `(nv,)` |
| `ctrl` | actuator control input | `(nu,)` |
| `xpos`/`xipos` | body frame / COM Cartesian position | `(nbody,3)` |
| `xquat`/`xmat` | body orientation (quat / rot. matrix) | `(nbody,4)`/`(nbody,9)` |

> **Important:** derived quantities (e.g. `geom_xpos`) aren't auto-refreshed when `qpos` changes — call `mj_kinematics(model, data)` to propagate.

**Simulation loop:**
```
qpos, qvel → mj_step(model,data) → viewer.sync() → (pace to real time) → new state ↺
```
- `mj_step` integrates $\dot x_{t+h}=f(x_t)$ one `model.opt.timestep` forward, using `qpos`, `qvel`, `ctrl`, contacts.
- `viewer.launch_passive(model,data)` = non-blocking; **you** drive timing and call `mj_step`/`sync()`.
- `mujoco.Renderer` + `update_scene`/`render()` = offscreen alternative (headless/video).
- **`viewer.sync()` only displays state — it never advances physics.**
- Interactive perturbation: double-click body, Alt+Ctrl+drag = force, Alt+drag = torque.

**Physics params** (`model.opt`: gravity, timestep, integrator, contact flags) — settable in XML (`<option .../>`) or Python (`model.opt.gravity = ...`). Chaotic multi-link pendulum demo shown, but no quantitative conclusion drawn — purely qualitative illustration of multi-body dynamics.

**`MjSpec`** — brief preview only: build a model in Python (`spec.worldbody.add_body/add_joint/add_geom`, `spec.compile()`) instead of raw XML. No deep dive.

**Actuation/control:**
- Generic PD law (pure control theory): `torque = kp*(q - q_des) + kd*(0 - v)`.
- Writing to `data.ctrl` does **nothing** unless a matching `<actuator>` (e.g. `<motor joint="..." gear="1"/>`) exists in the model.
- With `<motor>`, `gear=1`, `actuator_gainprm[:,0]=1` → `ctrl` ≈ joint torque **in this specific setup only**.
- `data.act` = internal activation state for actuators with own dynamics (e.g. muscles) — mentioned, not used here.

> **Do not equate `data.ctrl[i]` with torque in general** — meaning depends on actuator type/gain.

### Key Takeaways
- `MjModel` = static blueprint; `MjData` = live state + derived quantities.
- No joint → no DOF, regardless of geometry.
- `nq`/`nv`/`nu` are independent; free joints are the clearest case of `nq ≠ nv`.
- Derived Cartesian quantities need explicit propagation (`mj_kinematics`/`mj_forward`/`mj_step`).
- Rendering (`viewer.sync`) ≠ simulating (`mj_step`) — always call both.
- `ctrl` requires a matching `<actuator>`; its physical meaning (torque/position/velocity) depends on actuator config.
- Physics options changeable via XML or `model.opt` in Python.

## Notebook 02 — Contact Analysis

### Core Idea: How MuJoCo Detects, Visualizes, and Quantifies Contact

MuJoCo's contact handling is **optimization-based** (per the original paper referenced).

**Free joint** — unconstrained 6-DOF rigid body:
```xml
<body name="box"><freejoint/><geom type="box" size=".1 .1 .1"/></body>
```
`qpos[0:3]` = position, `qpos[3:7]` = quaternion → 7 position values, but `qvel` is only 6-dim (3 lin + 3 ang). Concrete case of `nq ≠ nv`.

**Visualization only** (no physics effect):
```python
viewer.opt.flags[mujoco.mjtVisFlag.mjVIS_CONTACTPOINT] = True
viewer.opt.flags[mujoco.mjtVisFlag.mjVIS_CONTACTFORCE] = True
```
plus `model.vis.scale.contactwidth/contactheight/forcewidth`, `model.vis.map.force` for marker/arrow sizing.

**Contact pipeline:**
```
geom positions (from qpos) → collision detection → contact generation
   → constraint/contact solver → contact forces → generalized forces → accelerations
```

**Reading contact data:**
| Source | Gives |
|---|---|
| `data.contact[i].geom1/geom2` | which geoms are touching |
| `data.contact[i].friction` | friction coeffs (5 values) |
| `data.contact[i].dist` | penetration/separation distance |
| `data.ncon` | # active contacts |
| `mujoco.mj_contactForce(model,data,i,forcetorque)` | 6-vec: [0]=normal force, [1:3]=friction (tangential), [3:6]=torque — **in the local contact frame, not world frame** |

**Experiment 1 — random orientation drop:** box dropped with randomized quaternion; force/`ncon`/normal-force-vs-`mg`/penetration plotted.
- **Observed:** at rest, normal contact force balances weight ($F_z \approx mg$, per Newton's 2nd law) — a basic instance of contact force resolving an external load.
- **Penetration:** MuJoCo's default contact is **compliant/soft** (`solref`/`solimp` geom attributes) → small nonzero penetration is normal, not a bug. No quantitative solref↔penetration relationship is derived in the notebook — only shown qualitatively.

**Experiment 2 — friction sliding vs. tipping:** box given initial horizontal velocity; `friction` attribute varied.
- **High friction (2):** box **tips** (friction arrests contact-point sliding fast → momentum creates torque about contact edge).
- **Low friction (0.1):** box **slides** (contact point slips, momentum dissipated as translation).
- **Principle:** friction coefficient directly governs slide-vs-tip response — relevant to legged locomotion / manipulation contact planning.

### Key Takeaways
- `<freejoint/>` = full 6-DOF; `qpos` 7-dim (incl. quaternion), `qvel` 6-dim.
- Contact visualization flags are cosmetic only.
- Pipeline: detection → generation → solver → forces → generalized forces → accelerations.
- `mj_contactForce` output is in the **local contact frame** (normal + 2 friction dirs), not world XYZ.
- Default contact is compliant (`solref`/`solimp`) — expect small penetration, not rigid zero-penetration.
- **Detection ≠ force computation**: `data.contact`/`ncon` tell you *that* contact exists; `mj_contactForce` gives the *resolved force*.
- Friction magnitude qualitatively controls tip vs. slide behavior.

## Notebook 03 — 3D Finger EDU

### Core Idea: Same Vocabulary, Applied to a Real Multi-DOF Robot

Goal: load a real 3-DOF arm (Open Dynamic Robot Initiative "Finger EDU"), PD-control it to a pose, analyze the transient, then hit a cube and analyze that contact — directly reusing Notebook 01's controller/loop and Notebook 02's contact-force/plotting code.

- **URDF → MJCF:** original description is URDF (incompatible with MuJoCo natively); pre-converted for the tutorial.
- **Scene composition:** `finger_edu_scene.xml` uses `<include file="finger_edu.xml"/>` to import the bare robot (no floor) without duplicating it — reusable modular pattern.
- **PD controller generalized to vectors:** `torque = kp*(q_des - q[:n_act]) + kd*(0 - v)[:n_act]`; same loop structure as before, `data.ctrl = torque[:model.nu]` (note explicit slicing → **`nv` need not equal `nu`**, reinforcing NB01's warning).
- **Logging > watching:** `sim_data` dict collects `qpos`/`qvel`/`ctrl`/`time` each step → plotted in 3 stacked subplots. Viewer = qualitative intuition; logging+plotting = quantitative diagnosis (overshoot, oscillation).

**Experiment — gain tuning:** initial gains produce "quite some oscillations" (notebook's own words). Task: increase `KD` and re-plot.
- **Why more `KD` helps:** proportional term (`KP`) alone → underdamped/oscillatory response in an inertial system; derivative term (`KD`) dissipates energy → moves toward critical damping. Classic PD damping trade-off.
- **No specific tuned value is given in the notebook** — `KD`/`Q_DES` are left as reader exercises; don't treat any particular number as "the" answer.

**Adding a manipulated object + filtering contacts:**
- New scene (`finger_edu_scene_cube.xml`): free-joint cube (mass 0.01) added near the arm's workspace.
- Problem: cube touches **both floor and robot** → naive `data.contact` sum conflates both interactions.
- Fix: resolve `floor_id = mj_name2id(...)` once, then in `plot_contacts`, `continue` (skip) any contact where `geom1` or `geom2 ∈ discard_contacts_id`.
- **General pattern:** with >2 objects in a scene, always filter `data.contact` by geom ID to isolate the interaction of interest.
- Final analysis (max penetration / max force) reuses NB02's plotting tools — **notebook doesn't report specific numeric results**, only asks the reader to read them off the plot.

### Key Takeaways
- URDF must be converted to MJCF; `<include>` enables modular scene reuse (robot ± extra objects).
- Controller/loop pattern scales from scalar to vector joints without structural change.
- Quantitative tuning needs logging+plotting, not just the viewer.
- Higher `KD` → more damping → less oscillation (standard PD trade-off); no specific gain value is prescribed.
- With multiple contact-capable objects, filter `data.contact` by geom ID to isolate the pair of interest.
- This notebook adds **no new core concepts** — it's an integration/application exercise proving NB01–02 concepts scale to a real robot.

## Quick-Reference: Common Pitfalls

| Pitfall | Why Wrong | Fix |
|---|---|---|
| Body has geoms → assume it has DOF | DOF comes only from joints | Add explicit `<joint>` |
| Assume `nq == nv == nu` | Free joint: `nq`=7 ≠ `nv`=6; `nu` independent | Check `model.nq/nv/nu` separately |
| Write `data.ctrl`, expect motion | No effect without matching `<actuator>` | Add `<actuator>` bound to the joint |
| Treat `ctrl[i]` as always = torque | Depends on actuator type/gain | Check actuator config first |
| Loop with only `viewer.sync()` | Never advances physics | Always call `mj_step` too |
| Read `xpos`/`geom_xpos` right after changing `qpos` | Not auto-refreshed | Call `mj_kinematics`/`mj_forward`/`mj_step` |
| Expect zero penetration | Contact is compliant by default (`solref`/`solimp`) | Treat small penetration as normal |
| Sum all of `data.contact` with >2 objects | Conflates unrelated contact pairs | Filter by `geom1`/`geom2` ID |
| Treat `mj_contactForce` output as world-frame | It's in the local contact frame (normal + 2 friction) | Index 0=normal, 1–2=friction, local frame |

## Final Cheat Sheet

**Core Objects:** `MjModel` (static, compiled) · `MjData` (mutable state) · `MjSpec` (programmatic model builder)

**Model Structure:** Body (movable/inertial) · Joint (DOF, no joint = fixed) · Geom (visual/collision shape) · `<freejoint/>` (6-DOF, `qpos`7/`qvel`6) · `<actuator>` (links `ctrl`→force; required for `ctrl` to do anything) · `<keyframe>` (named initial state)

**State:** `qpos (nq,)` · `qvel (nv,)` · `qacc (nv,)` · `ctrl (nu,)` · `time` · `model.nq/nv/nu` (independent counts)

**Kinematics:** `xpos/xipos (nbody,3)` · `xquat/xmat (nbody,4/9)` · `geom_xpos` · `mj_kinematics()` propagates `qpos`→Cartesian · `mj_name2id()` underlies named access

**Dynamics:** `mj_step(model,data)` — integrates one `model.opt.timestep` · `model.opt` — gravity/timestep/integrator/flags

**Contacts:** `data.contact` (geom1/geom2/friction/dist) · `data.ncon` · `mj_contactForce()` → [normal, friction×2, torque×3] in local frame · `solref`/`solimp` — contact compliance · `mjVIS_CONTACTPOINT/FORCE` — viz only

**Control:** PD law `kp*(q_des-q) + kd*(0-v)` · `data.act` — actuator internal state (muscles etc.)

**Simulation:** `viewer.launch_passive()` — non-blocking, you drive the loop · `viewer.sync()` — display only, no physics · `mujoco.Renderer` — offscreen frames/video

**Useful Functions:** `MjModel.from_xml_string/from_xml_path` · `mj_resetData`/`mj_resetDataKeyframe` · `mj_name2id`
